When NOT to Use Lethe

Honest assessment of scenarios where other systems excel.

Honest Assessment: Where Lethe Shouldn't Be Used

Low-entropy/Single-file Code

Why Lethe struggles: Lethe's diversification may over-complicate simple, focused tasks

Better choice: Zoekt for symbol-exact search

Use when: Single-file debugging, exact symbol lookup

Tiny Contexts (<1k tokens)

Why Lethe struggles: Planning overhead not justified for small contexts

Better choice: Direct BM25 or simple vector search

Use when: Short documents, simple QA

Strict Latency Requirements (<50ms)

Why Lethe struggles: Multi-stage pipeline adds unavoidable latency

Better choice: ColBERT with pre-computed indexes

Use when: Real-time applications, user-facing search

Domain-Specific Sparse Features

Why Lethe struggles: Generic sparse patterns may miss domain signals

Better choice: SPLADE with domain fine-tuning

Use when: Medical/Legal documents, specialized terminology

Fair Evaluation Methodology

Budget Matching

  • Keep Ratios: 8%, 15%, 30% of original context tokens
  • Consistent Tokenization: Whitespace-based for cross-system fairness
  • Budget Enforcement: All systems limited to same token budget

Statistical Rigor

  • Bootstrap Testing: 1000 iterations for confidence intervals
  • Permutation Testing: 1000 iterations for significance testing
  • Multiple Comparison Correction: Holm step-down method
  • Effect Size: Cohen's d with practical significance threshold (|d| > 0.1)

Vendor-Fair Configurations

  • Default Parameters: Each system's recommended defaults
  • Hybrid Modes: Using documented fusion approaches
  • No Cherry-picking: Same parameters across all datasets
  • Resource Limits: 8GB RAM, 4 CPU cores per container
